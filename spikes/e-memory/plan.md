# Spike E plan

Hypothesis: a pinned existing local-first MCP memory can replace a bespoke engine
while preserving project identity, dual-harness access and recoverability.
Timebox: 2–3 developer-days maximum. Stop a candidate on unavailable verified
package or credentials; retain executable offline/negative evidence and continue.

Candidates: Basic Memory current verified PyPI release; official MCP reference
memory server; current native Claude/Codex memory/context; synthetic custom
contract only. No private memory implementation, real notes or user profiles.

Run actual local tools for project separation and explicit wrong-project probes,
shared checkout identity, fresh process restart, concurrent writes, corruption
and restore, export/import/backup, offline retrieval, deletion and package removal.
Test exact-version protocol/version handshake and synthetic secret canary behavior.
Use isolated native provider MCP registration plus actual MCP sessions; do not
claim model-level recall from a direct protocol test. Compare both orders with
Rig for overlapping registrations. Separate application project selection from
an authorization boundary. Report retrieval precision on a fixed synthetic corpus
and response bytes, not invented model-token efficiency.

Default architecture must remain native memory plus optional proven local MCP;
no custom memory engine unless a measured critical advantage justifies it.
